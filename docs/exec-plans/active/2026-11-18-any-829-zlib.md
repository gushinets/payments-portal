# ANY-829 — production web zlib remediation

Issue: https://linear.app/paveldik/issue/ANY-829

## Plan and baseline

- [x] Fetch main and isolate work at `fb4d66bb0f9f24dbd18257366926697afaa46fe3`.
- [x] Characterize the unchanged final image and existing runtime coverage.
- [x] Update only the supported Alpine runtime package and enforce its security floor.
- [x] Compare final images with the same scanner database and verify runtime.
- [x] Run canonical checks and provide a draft PR for human review.

The unchanged final image uses Node 24.22.1, Alpine 3.24.3 and zlib 1.3.2-r1.
The existing runtime verifier checks package floors, non-root execution, removal of
build tools, compression round trips and native sharp processing. The proposed
`apk info --exists 'zlib>=1.4-r0'` regression exits 1 in the unchanged image.
Existing compression tests do not by themselves establish HTTP or HTTPS behavior.

[Alpine's security tracker](https://security.alpinelinux.org/vuln/CVE-2026-4738)
lists 1.4-r0 as fixed for 3.24. A disposable baseline container's `apk policy zlib`
listed 1.4-r0 in its configured stable 3.24 main repository. The smallest
supported change updates zlib from that repository, keeping the shared pinned
Node base intact; no edge repository or binary substitution is needed.
The tracker describes GDAL's bundled `contrib/infback9` code and links the
[upstream GDAL fix](https://github.com/OSGeo/gdal/pull/12244); this package
finding alone does not establish a reachable application exploitation path.

## Scan evidence

Trivy 0.72.0 scanned the actual local final images with `trivy.yaml`,
`.trivyignore.yaml`, `--scanners vuln,secret --format json --exit-code 0`
and `--skip-db-update`. Both used the same read-only v2 database: updated
2026-11-18T07:15:21Z, downloaded 2026-11-18T11:27:33Z. For reproduction, run the following POSIX shell commands from the repository
root. `TRIVY_DB_DIR` must name an absolute host directory containing `trivy.db`
and `metadata.json` from the chosen database snapshot. Retain that snapshot and
use it for both images; a newer snapshot can produce different findings.
Docker Desktop users should enable access to the host directories first.

```sh
export TRIVY_DB_DIR=/absolute/path/to/retained/db
mkdir -p .harness/any-829-reproduction
for variant in before after; do
  docker run --rm \
    --mount type=bind,src=/var/run/docker.sock,dst=/var/run/docker.sock \
    --mount "type=bind,src=$TRIVY_DB_DIR,dst=/root/.cache/trivy/db,readonly" \
    --mount "type=bind,src=$PWD/trivy.yaml,dst=/config/trivy.yaml,readonly" \
    --mount "type=bind,src=$PWD/.trivyignore.yaml,dst=/config/ignore.yaml,readonly" \
    --mount "type=bind,src=$PWD/.harness/any-829-reproduction,dst=/reports" \
    aquasec/trivy:0.72.0 image --skip-db-update \
    --config /config/trivy.yaml --scanners vuln,secret \
    --format json --exit-code 0 --timeout 15m --ignorefile /config/ignore.yaml \
    --output "/reports/$variant.json" "payment-portal-web:any829-$variant"
done
python scripts/repo.py trivy redact .harness/any-829-reproduction
```

The configuration mounts are read-only. `/reports` is a writable host bind
mount, so both JSON files persist after container removal and the host-side
redaction command processes those same files.
The redactor reported zero secret values in both reports. Sanitized report
SHA256: before `a18ebb2df4b5294afe1d8385324bd29d670c942660f93da351e477dedd53c3ab`;
after `088a290b3c09c8fb63366cac14c76a39407aafd882f53e95847dfe2b8aa973ce`.
The before report contained CVE-2026-4738 and two unrelated Medium Next.js
findings, CVE-2026-119351 and CVE-2026-119790 (16.4.2, fixed 16.4.5). The after
report retained both Next.js findings and removed the zlib finding; neither
report contained Critical or High vulnerabilities. Scan enforcement and
exceptions were unchanged. PR #166 is closed without merge; its web patch
proposed Node 26.13.0, outside the required Node 24 runtime, alongside a uv
update. It is not a suitable prerequisite for this targeted change.
