## Plan overview and exact outcome

**Step 7 implementation outcome (achievable now).** Against the deliberately created **real-HTTP Kernel mock** and isolated recorded LBX transport/test commercial and legal fixtures, the user can review an offer, explicitly confirm its exact terms (and recurring/autopay terms **only when applicable**), create one durable `PurchaseIntent`, run customer → dedicated agreement → subscription preparation with exact simulated readback, resume an uncertain result and reach a **Widget SDK stub** or Manage state. Real Portal routes, persistence, concurrency and frontend wiring must work; only the external endpoints and test evidence are simulated. A **targeted, separately authorized account check** is needed only if the selected LBX account configuration cannot be established from ANY-634 plus current admin/Server API reads; it is not a Step 7 local implementation DoD. None of this grants paid access. **Real-sale outcome (later):** after real Kernel/paid vocabulary, approved LBX profile and final commercial/legal terms are enabled, the same code path—without fake evidence—permits an actual verified LBX Widget.

**End-to-end observable sequence:**

```text
Browser (localized product/account; simulated development offer or approved historical terms)
  -> authenticated offer review and explicit legal/recurring acceptance
  -> POST purchase with client Idempotency-Key
  -> DB lookup: exact replay / occupied product scope / genuinely new operation
  -> ONLY for new: bounded fresh complete Kernel manifest + LBX selected-offer reads
  -> material equality to current independently approved immutable mapping
  -> short PostgreSQL transaction: unique product-scope hold + opaque customer slot
       + purchase-bound legal event + immutable PurchaseIntent + idempotency identity
  -> commit; no outbound HTTP inside that transaction
  -> before each NOT-YET-SENT CREATE: fresh check of originally accepted terms
  -> committed outbound operation (possible-send state/correlation) -> one LBX POST
  -> authoritative point GET and ownership/material proof; link safely
  -> GET purchase/status / explicit safe continue or read-only discovery
  -> separately authenticated Widget-open request -> fresh identity/material proof
  -> backend-signed type-7 JWT, response no-store; frontend Widget mount/teardown
  -> zero paid grants, zero Portal payment actions
```

**Development boundary:** The Kernel mock runs as a separate local HTTP service and returns the contract-shaped **real Kernel product ID `proposal_ai`** but a **test-only** metric `proposal_ai.test_generations` with unit `generation`. **Metric** means *what is counted* (generations/operations); **allowance** means *how many are sold per billing period* (e.g. 100)—the latter is independently configured in the approved mapping, **not read from LBX** and **not inferred from guest quota**. Do not hardcode test metric or a sample allowance into Application/DB schema/Portal wire. Mock remains `SIMULATED` in Step 6/7; use its fault scenarios to validate the architecture. Missing G1–G4 never stops isolated coding; inability to prove a real paid product only disables real-sale enablement.

**Essential safety results.** Concurrent same-user/product attempts cannot duplicate active preparation; same key + same canonical accepted meaning returns the same intent; changed meaning conflicts. Browser close/reload, preflight outage, lost LBX response and process restart do not silently reprice, release an unpaid subscription, retry an ambiguous POST, mint on incomplete proof, or grant access. Provider IDs, balances and secrets are not public contract fields.

**Non-goals:** no Portal `Order`, checkout session, card capture, provider payment orchestration, refunds, universal billing adapter/registry, whole-account tariff mirror, extra publication/admin API ([ANY-690](https://linear.app/paveldik/issue/ANY-690)), autonomous webhook/reconciliation/UNKNOWN worker (Step 8), paid eligibility and allowances (Step 9), Kernel runtime access/quota (Step 10), or full live billing/paid E2E and launch (Step 11). ### 2.2 Persisted ownership: exact scope, customer slot and immutable accepted meaning

**Chosen scope design (narrow warranted migration).** The current unique idempotency key and `ix_purchase_intents_user_product` are insufficient to prevent **two different keys** starting simultaneous purchases. `billing_product_access_scopes` is a distinct access-primary-selection table; do not overload its meaning. Add one minimal **purchase-scope hold row** (e.g. `billing_purchase_scope_holds`) per `user_id,product_id`, with unique DB key and scoped link to owner `PurchaseIntent` and/or validated existing `ExternalSubscription`, current account/tenant/region provenance, hold status, monotonic ownership epoch, timestamps, release evidence/audit. For provider binding also add/verify **account-scoped partial unique non-null** external IDs: `(external_billing_account_id, provider_customer_id)` for customer slots, `(external_billing_account_id, external_subscription_id)` and `(external_billing_account_id, external_agreement_id)` for linked subscription records. **Subscription-row uniqueness alone is too late for dedicated agreements:** immediately after agreement point-read and before subscription CREATE, also enforce a durable unique `(external_billing_account_id, operation_kind, bound_external_object_id)` binding on resolved create operations with a non-null provider ID. Narrowly add `external_billing_account_id` to `ExternalCreateOperation`, backfill it from its required customer slot, enforce a composite FK to `(customer_id, external_billing_account_id)` (add the minimal corresponding customer-side unique target) and a partial unique index on resolved non-null bound IDs. This forbids two parallel preparations from reusing one provider agreement even before either has a linked subscription. Currently these IDs have *non-unique indexes*, so readback alone cannot prevent two Portal rows from binding the same LBX object/agreement. Add focused cross-user and cross-account cases; fail a populated migration on conflicts rather than inventing a winner. Prefer using the existing composite FK/unique provenance keys; **the proposed table name is illustrative, not permission to create a generic subsystem**. Always lock this row for scope changes (`SELECT ... FOR UPDATE`) in a short transaction; on initial concurrent insertion resolve the unique violation by rolling back/retrying the **entire short transaction with a fresh session** before reading/locking the winner (never continue a failed SQLAlchemy transaction). Existing linked non-terminal external subscriptions, including those without a PurchaseIntent, **must be checked when the hold is first created**; any Step 8 discovery/import writer must acquire the same product hold and use its epoch, or a concurrent unknown subscription can bypass the invariant. Historical rows without a hold must be backfilled or safely treated as occupied before admitting a new purchase. An indexed unique `(user_id,product_id)` row is the serialization point **across both intents and linked nonterminal subscriptions**. Do **not** instead add a simplistic partial index on `PurchaseIntent.state`: `linked` remains historical even after a subscription becomes terminal, and an independently discovered subscription may have no intent.

**Atomic reservation transaction** (after bounded live admission, which holds **no SQL transaction**): recheck same-key identity and existing hold/subscriptions, verify exact current latest approved mapping/revision, allocate or lock the one hold, create/reuse unique `(account,user)` customer slot with immutable `billing_customer_key`, append a **commercial** `LegalAcceptanceEvent` with exact `(account,offer,fingerprint)`, append current `DocumentAcceptance`s for required document versions/text hashes (including `RECURRING_CONSENT` where required), and insert one immutable `PurchaseIntent` with deterministic schema-versioned accepted snapshot and `client_idempotency_key`, point the hold to it, then commit. Do not write a new legal event on exact replay. On transaction/commit uncertainty, reread by key and hold; do not start a provider CREATE on an unproven commit.

**Snapshot `accepted_snapshot_schema_version=v1` content (same structure for explicitly labelled simulated/local development, and later genuine evidence):** configured tenant/region/account, user and product, offer + mapping revision/number/digest, Kernel metric/unit/integer approved allowance, accepted commercial fingerprint and normalized selected-source provenance, LBX tariff/service/period refs **inside private persistence only**, exact selected/default component IDs/quantities/effective service unit and connection price, total recurring and initial amounts with ISO currency/decimal scale/units, period length/anchor, prepaid/block/discount/tax/activation/renewal/cancellation/historical policy, configured seller organization and approved seller/legal revision references, required actual `DocumentVersion` IDs/version/hash/acceptance-text hashes, accepted-at and operator-vetted evidence basis. Never store only a scalar tariff price; LBX service `multiplicator` is **not** Kernel allowance. A change requires **new acceptance/new revision for a new purchase**, not mutation to this snapshot. Sensitive proof fields stay private, not logged or sent to the browser.

**Release:** hold survives a linked **prepared/unpaid** subscription indefinitely despite browser TTL/reload. It can be cleared/reassigned only after authoritative no external effect, verified terminal subscription **and** absence of other unresolved creates, or an audited support operation with proof. A conflicting late external object after manual release enters review, not automatic access. Step 8 must use this same lock/hold for independently discovered subscription decisions, not create a parallel scope owner. `billing_product_access_scopes.primary_subscription_id` remains owned by Step 8/9 selection semantics and is neither minted nor treated as purchase reservation here.

**Outbound operation fencing:** persist `ExternalCreateOperation` before **any possible** customer, agreement or subscription POST. Existing customer unresolved partial unique index is reusable. Add a minimal permanent at-most-one-(purchase-intent, kind) uniqueness for agreement/subscription and a unique opaque `request_correlation_key` for every create operation. Use the new operation account scope and partial unique provider-ID binding to reject duplicate customer/agreement/subscription links **before** proceeding to the next CREATE; do not postpone agreement deduplication until the subscription projection is inserted. The operation's committed state means `unsent` / `possible_send` / `unknown` / `bound` / `failed_before_send` / `manual_review` (typed application vocabulary on the existing `TEXT` field). A durable `possible_send` **must be interpreted as potentially sent after crash**, even if no network packet was actually transmitted; no new attempt is allowed until authoritative no-effect proof. A **single conditional DB claim/CAS** (`unsent -> possible_send` with an ownership epoch/fence, under row lock) before actual send prevents two process/HTTP continuations sending the same operation simultaneously; transaction releases **before** network. **In that SAME transaction, before any provider I/O, set `unknown_since=send_claim_at`, set `unknown_recovery_deadline_at=unknown_since+2h`, and insert or claim the unique durable due `BillingWorkItem`.** Otherwise a crash after `possible_send` but before a later UNKNOWN transition leaves no durable 2-hour deadline. This is a conservative *potential send* clock, not proof the POST reached LBX. A definite pre-send refusal does not set the clock. Successful authoritative readback resolves the operation and makes its due item harmless/terminal; `possible_send` after crash is UNKNOWN and can only be recovered by read-only proof. Late responses must compare the persisted epoch/fence before binding; no request or worker may reset `possible_send` to `unsent` based solely on elapsed time. Ensure one work item per operation via locking and/or a narrow partial unique coalescing index, not the existing non-unique `ix_billing_work_items_coalescing_key`. One customer slot may be used by multiple product intents, but concurrent customer CREATE uses the same customer operation/scope lock. Do not reuse a dedicated agreement for a different subscription.
