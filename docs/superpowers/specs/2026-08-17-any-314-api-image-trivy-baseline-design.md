# ANY-314 API image Trivy baseline design

Status: approved design
Date: 2026-08-17
Linear: https://linear.app/paveldik/issue/ANY-314/ustranit-trivy-baseline-dlya-api-production-base-image

## Goal

Make the production API image compatible with the checked-in Trivy enforcement
policy without changing Python application dependencies or API behavior. Apply
all Debian security fixes currently available to the image and record narrowly
scoped, human-approved, expiring exceptions for the four remaining Critical
`perl-base` findings that Debian Trixie cannot yet fix.

## Measured baseline

The authoritative `trivy-reports-31792790500-1` artifact was generated by
Trivy 0.72.0 from repository commit
`a1ff0728fe9e230a99c362f3f2232f916c5d3166`. Its `api-image.json` report
identified Debian 13.5, `perl-base 5.40.1-6`, and these four Critical findings:

- `CVE-2026-13221`;
- `CVE-2026-42496`;
- `CVE-2026-57433`;
- `CVE-2026-8376`.

None had a fixed version in the artifact. The report contained no fixable High
API-image finding at that time.

On 2026-08-17, the current multi-architecture manifest for
`python:3.12-slim` was
`sha256:2c941e860699f878900b0edc2403613c234d4b32eda3cc9fa7036991a2a63c4a`.
The image identifies itself as Python 3.12.14 on Debian 13.6 and still contains
`perl-base 5.40.1-6`. A fresh Trivy 0.72.0 scan reproduced the same four
Critical findings. It also reported nine fixable High findings for packages
from the `util-linux` source package, for which Debian publishes
`2.41.5-0+deb13u1`.

The Debian Security Tracker still marks Trixie's `perl 5.40.1-6` as vulnerable
to all four CVEs:

- https://security-tracker.debian.org/tracker/CVE-2026-13221
- https://security-tracker.debian.org/tracker/CVE-2026-42496
- https://security-tracker.debian.org/tracker/CVE-2026-57433
- https://security-tracker.debian.org/tracker/CVE-2026-8376

The open grouped Dependabot pull request
https://github.com/gushinets/payments-portal/pull/30 updates the API base to
Python 3.14 and the web base to Node 26. It does not provide a same-line Python
3.12 digest refresh, still inherits Debian Trixie, mixes an unrelated web
runtime major update into the change, and is therefore not a remediation for
ANY-314.

## Considered approaches

### Selected: refresh, upgrade available OS packages, and except only unfixed CVEs

Pin the current `python:3.12-slim` multi-architecture digest, apply available
Debian stable package upgrades in the shared API base stage, and leave Python
application dependencies untouched. Suppress only the four unfixed
`perl-base` CVE IDs, scoped to the Debian package PURL and expiring on
2026-09-30.

This approach removes every finding for which Debian has already published a
fix, preserves the repository's Python 3.12 runtime baseline, and makes the
remaining upstream risk explicit and time-bounded.

### Rejected: wait for a fully fixed upstream image

Waiting would avoid an exception, but Debian has no Trixie fixed version for
all four findings and no committed delivery date. ANY-314 and
`TRIVY_ENFORCE=true` would remain blocked indefinitely.

### Rejected: change the runtime distribution or Python major

Moving to Alpine, distroless, or Python 3.14 could avoid a particular Debian
package inventory, but it changes the runtime and wheel compatibility surface.
The grouped Dependabot change also modifies the unrelated web runtime. That is
materially broader than the base-image baseline remediation requested by
ANY-314.

Installing Perl from Debian unstable or experimental was also rejected. It
would mix release channels in a production payment-service image and does not
provide a stable fix for all four CVEs.

## Image remediation

`apps/api/Dockerfile` will retain the `python:3.12-slim` tag and replace its
existing digest with the measured current multi-architecture digest. The
shared `base` stage will run a non-interactive Debian package refresh and
upgrade, then remove `/var/lib/apt/lists`. No new OS package is introduced.
Because every later API stage derives from `base`, the production and
development images receive the same patched OS baseline.

The base digest remains reviewable and architecture-independent. The package
upgrade deliberately consumes Debian's current stable security repository so a
rebuild can receive security fixes released after the upstream Python image.
Final evidence must record the installed package versions and the image digest
used for the scan.

## Temporary exception contract

The four entries in `.trivyignore.yaml` will use only Trivy-supported filtering
fields:

- `id` identifies one of the four CVEs;
- `purls` contains `pkg:deb/debian/perl-base`, which scopes the exception to the
  inherited Debian package;
- `statement` names the affected `payment-portal-api` production image and
  `apps/api/Dockerfile`, explains that no Trixie fix existed on 2026-08-17,
  identifies `@gushinets` as owner, and links the removal work to ANY-314;
- `expired_at` is `2026-09-30`.

Trivy's path filter cannot scope this OS-package finding because the report has
no `PkgPath`. The package PURL is therefore the functional scope, while the
affected image and source path remain explicit in the statement.

The repository exception test will require every future entry to have an ID,
non-empty reason, expiry, and at least one functional path or package-PURL
scope. It will also require the statement to identify both an owner and an
affected image or path. `docs/SECURITY.md` will describe this OS-package
exception form so future maintainers do not add a path that prevents Trivy from
matching the finding.

The owner is the existing security CODEOWNER, `@gushinets`. Human review of the
exception remains mandatory. Expiration is enforced by the existing date-based
test, so an unremoved exception will fail repository checks after 2026-09-30.

## Verification

Implementation will follow a configuration-focused red/green cycle:

1. strengthen the exception-policy test and observe it reject the approved
   entries before they exist;
2. add the four entries and observe the focused policy test pass;
3. update the API base image and build the `production` target;
4. inspect the built image to confirm its non-root `app` user, production
   command, Debian version, Python version, `perl-base` version, and upgraded
   `util-linux` package versions;
5. run a production-image smoke that imports the application from the final
   image and exercises API liveness without collecting secrets;
6. run a raw Trivy 0.72.0 image scan without the ignore file, proving that all
   fixable High findings are gone and exactly the four approved Critical
   findings remain;
7. run the workflow-equivalent scan with `.trivyignore.yaml`, proving that the
   API report has zero blocking findings;
8. run the focused Trivy policy tests, backend tests, Dockerfile compatibility
   tests, documentation checks, and the broadest supported canonical check;
9. push the branch and confirm the `Security scans` workflow builds and scans
   the production image successfully.

`TRIVY_ENFORCE` is a repository Actions variable and will not be changed by the
code change. The pull request will state that enforcement may be enabled only
after the exception receives its required human approval and the change is
merged.

## Evidence and workflow updates

The pull request body and an ANY-314 Linear comment must both record:

- the original artifact and its four Critical findings;
- the old and refreshed Python image digests;
- the rebuilt image's Debian, Python, `perl-base`, and patched package versions;
- whether a fixed upstream image was available at verification time;
- the Debian tracker status for every excepted CVE;
- the exception owner, scope, reason, and 2026-09-30 expiry;
- raw and filtered Trivy summaries;
- production build, smoke, backend, canonical, and `Security scans` results;
- the administrator follow-up for `TRIVY_ENFORCE=true`.

The Linear issue will remain in progress until the pull request is ready for
human review. Merge approval, exception approval, and enabling the repository
variable remain human actions.

## Scope and rollback

The implementation will not update FastAPI, Uvicorn, Poetry, the lockfile, or
any Python application dependency. It will not change web images, GHCR
publishing, API behavior, migrations, payment logic, or legal content.

The Dockerfile digest/package-refresh change and the four exception entries can
be reverted without data migration. If Debian publishes a fixed Trixie package
before implementation finishes, the preferred path is to rebuild with that fix
and omit every exception no longer needed. After merge, the owner must remove
each entry as soon as its CVE no longer appears, without waiting for the expiry
date.
